# Database & data

## Constraints from the specs

- The storage mechanism for V1 is the squad's choice — "a simple storage mechanism" (HAC-PROD-001 §9).
  Detailed relational / NoSQL persistence design is **V2** scope (HAC-TECH-001 §3.3).
- PULSE must **not** access the historical HealthAI Coach PostgreSQL database (HAC-TECH-001 §4.3).
- Only the synthetic data of HAC-DATA-001 may be used (RG-CONF-03). No real employee data, ever.
- The application must start and be demonstrable from the repository alone (ACC-GEN-01), and changes must survive
  a page refresh / new read (ACC-PREF-04, ACC-ADM-06).
- No secret in the repository: datasource credentials come from environment variables (ACC-SEC-01).

## Proposed choice for V1

- **H2**, loaded at startup with fixtures, so anyone can clone and run without an external service.
  - Default: in-memory (data reset at each restart — fine for acceptance).
  - Optional: file mode (`jdbc:h2:file:./data/pulse`, git-ignored) to keep changes across restarts.
- Schema generated by Hibernate (`ddl-auto`) for V1; versioned migrations (Flyway) to be introduced with the V2 persistence design.
- **Supabase (PostgreSQL)**: optional `prod`-like profile only, credentials via environment variables.
  Claude Code can inspect it read-only through the `supabase` MCP server (`.mcp.json`). Not required for the V1 demo.

Profiles (proposal): `dev` (default, H2 + fixtures) · `supabase` (PostgreSQL, env vars `DB_URL`, `DB_USER`, `DB_PASSWORD`).
